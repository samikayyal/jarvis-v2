# Stealth-browser exploration

Research date: 2026-10-16. This note evaluates three Selenium-compatible approaches for the Google unusual-traffic incident. It is a compatibility and risk review only. No package was installed, no browser experiment was run, and no CAPTCHA or Google challenge was interacted with.

## What the evidence says about the incident

The isolated headed-Xvfb diagnostic reached Google's `/sorry/index` in 4.34 seconds and reported `Google blocked automated search traffic`; the proxy itself did not report a block. See [headed-browser-diagnostic.md](./headed-browser-diagnostic.md). Google's own support page says the message can be caused by automated traffic from the network, including a VPN, shared network, or IPv6 tunnel, and recommends checking malware, the network administrator, or the VPN provider. A browser fingerprint change therefore cannot be treated as a fix for network reputation: [Google Search Help](https://support.google.com/websearch/answer/86640?hl=en).

The strongest package-level caveat comes from the `undetected-chromedriver` maintainer: its README explicitly says that it does not hide the IP address and that datacenter or low-reputation home IPs may still fail. That is directly relevant to this result: [undetected-chromedriver README](https://github.com/ultrafunkamsterdam/undetected-chromedriver#readme).

## Compatibility and security conclusions

The existence of a matching Chrome 155 build is not the same as package compatibility. The sources establish only that Chrome for Testing publishes a matching driver, not that any of these packages correctly patches or controls Chrome `155.0.8059.39` under Python 3.14. SeleniumBase has the strongest current Python metadata, but its Selenium dependency does not match this repository and its network/lifecycle behavior is broader than the current contract. The other two packages provide no current Python 3.14/Chrome 155 evidence.

Jarvis's current reader configures `--enable-sandbox`, a fresh `--user-data-dir`, a localhost `PublicNetworkProxy`, blocked non-HTTP schemes, denied downloads, and CDP script disabling before navigation. A stealth layer that registers document-start scripts must be tested against that exact ordering: injection must be enabled only in the narrowly authorized search context, and it must not become a way for ordinary page reads to execute JavaScript. A framework that performs requests or driver downloads outside the reader would need a separate, security-reviewed network adapter; passing a proxy string alone is not proof that Jarvis's DNS, destination, redirect, and budget rules still hold.

## Recommended bounded experiment

1. Start with a **mocked/offline compatibility harness**, separate from production `SeleniumPageReader`. Use the installed Chrome/ChromeDriver paths and a fresh temporary HOME/profile only if a real browser is needed. Do not relax the production proxy to make a localhost fixture reachable.
2. Compare stock Selenium with one narrow, opt-in injection set at a local fingerprint fixture. Record only `navigator.webdriver`, UA/client hints, languages, plugins, WebGL vendor/renderer, `chrome.runtime`, and outer dimensions. The test should demonstrate that the requested values are internally consistent and that document-start registration occurs before navigation; it should not contact Google, CAPTCHA sites, or a bot-bypass test service.
3. Assert the existing invariants: sandbox remains enabled; no driver/package download occurs at request time; no personal cookies or credentials are read; non-HTTP schemes and downloads remain blocked; public-network validation stays in the proxy; cancellation removes the temporary profile and all Chrome/ChromeDriver/Xvfb descendants.
4. Only if the narrow adapter passes those checks should it be considered for a single, low-volume live validation against an allowed public page. On any Google challenge, stop and preserve the blocked diagnostic. Do not interpret a change in CAPTCHA behavior as proof that the IP/network issue is solved.

This ranking makes the minimal adapter the only sensible first candidate. `selenium-stealth` is a possible later implementation component if its old JavaScript remains compatible with Chrome 155, but that compatibility is currently unknown. SeleniumBase and direct UC should remain comparison references until their extra request paths, driver downloads, sandbox defaults, license implications, and child-process cleanup are resolved.
