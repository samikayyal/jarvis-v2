Status: ready-for-agent

## Problem Statement

The authorized operator needs one dependable way to ask Jarvis, through the dedicated WhatsApp account, to read connected information, make explicitly approved changes, and run bounded work on the appropriate execution host. The completed messaging gateway provides transport but intentionally does not provide assistant behavior, authorization, orchestration, memory, connected-service access, or terminal execution.

Jarvis Assistant V1 must add that behavior without weakening the verified messaging gateway or turning a model into an authorization authority. It must remain completely reactive, support only the authorized operator, accept and return text only, keep one active request and one pending action at a time, preserve exact-action approval, and fail closed when identity, policy, audit, connector, worker, or external outcomes are uncertain. It must also fit the existing low-resource Ubuntu control host, support the personal Windows laptop only when selected and available, and keep trust-critical activation under manual administration.

## Solution

Build Jarvis Assistant V1 as a small server-side Python control plane beside the existing OpenWA messaging gateway. A signed `message.received` event admits a direct text message only after signature, session, event, message, and canonical authorized-operator checks. A deterministic capability broker then owns the working session, active request, pending action, control grammar, policy decisions, command permissions, replay protection, audit gate, and connector or worker dispatch.

An OpenAI Agents SDK orchestration agent over Responses interprets the admitted natural-language request, gathers bounded read-only context, selects the execution host when terminal work is needed, and creates typed proposals. It has no direct authority over credentials, Jarvis state, approvals, connected-service mutations, OpenWA delivery, the knowledge vault, or execution workers. Codex is available only as a bounded server-side specialist. Closed connectors expose the approved Gmail, Google Drive, knowledge-vault, outbound-messaging, and execution-worker capabilities. Google Calendar is not part of Jarvis v1.

Approval-gated actions are frozen, displayed exactly, and executable once only after a deterministic whole-message confirmation from the authorized operator. Terminal authorization uses deterministic policy precedence and narrow command permissions; no model-based classifier participates in V1. Jarvis retains the defined local conversation history, explicit durable assistant memory, operational state, redacted append-only audit record, and full diagnostic traces indefinitely while keeping credential-path material in isolated service-specific plaintext credential files.

Jarvis runs as an independently operated, resource-bounded deployment. OpenWA remains a separate pinned deployment and the sole messaging gateway. Automated verification uses one primary control-plane seam, and initial activation additionally requires the separately defined supervised acceptance suite against real OpenWA, Google, the knowledge vault, Ubuntu, and Windows.

## Implementation Decisions

### Product boundary and action matrix

- V1 is completely reactive. Only an admitted inbound request may start assistant behavior. Milestone and completion messages belong to that originating request; scheduled work, reminders, monitoring, and unsolicited assistant messages are excluded.
- V1 has one authorized operator, identified through one configured canonical direct-message JID. It has one active request, one pending action, one terminal action, and no request queue.
- The assistant interaction accepts and returns text only. Unsupported media may reach the messaging gateway but is not downloaded, interpreted, or answered by assistant behavior.
- Google reads cover bounded Gmail and Google Drive operations. Gmail send/reply operations are approval-gated. Calendar operations, Drive mutations, and destructive Google operations are not exposed.
- Knowledge-vault reads and deterministic search are allowed. Knowledge-vault writes require an exact approval-gated commit and normal push. Deletion, rename, non-Markdown mutation, force-push, history rewriting, and autonomous conflict resolution are excluded.
- Terminal actions may target Ubuntu or the personal Windows laptop. Ubuntu is the default execution host; the orchestration agent selects Windows only when explicit intent or task dependencies require it. An unavailable selected execution host never fails over or queues automatically.

### Runtime and authority

- The primary runtime is a server-side Python service using `uv` for dependency management and execution.
- The orchestration runtime uses the OpenAI Agents SDK over Responses. Jarvis, not an OpenAI-hosted conversation object or interactive Codex application, owns lifecycle, policy, approval, host, cancellation, and durable-state authority.
- The default model is explicit `gpt-5.6-terra` with `medium` reasoning. Canonical session choices are `gpt-5.6-sol`, `gpt-5.6-terra`, and `gpt-5.6-luna`; reasoning choices are `none`, `low`, `medium`, `high`, `xhigh`, and `max`. Availability failure never silently changes either selection.
- Coordinator tool calls are sequential in V1. Tools use strict, bounded typed schemas. Read tools return bounded data; mutation and terminal tools return proposals and cannot dispatch side effects.
- Codex is a bounded server-side specialist, primarily through its MCP server under the Agents SDK. It is read-only by default and constrained by configured execution host, canonical working directory, model, reasoning, sandbox, approval policy, timeout, and allowed operations. Workspace-write mode requires an already approved exact Jarvis proposal and an allowlisted workspace; push, history rewriting, and `danger-full-access` remain unavailable. Codex's own command and file approvals must stay visible and consistent with Jarvis approval, and a never-approve configuration cannot be used to bypass Jarvis authorization for mutating work. Codex returns a typed result, but its prose is not evidence that a mutation or command succeeded; the relevant adapter independently verifies changed paths, repository state, and test or execution outcomes. A replaceable SDK or app-server adapter may be used only if stronger interruption or typed-event control is required.
- The orchestration agent and Codex are non-authoritative. Model output, Codex output, terminal output, quoted text, and connected-service content cannot establish identity, approval, policy, permission, or connector authority.

### Reference-monitor architecture

- A process-isolated capability broker is the deterministic reference monitor and sole authority for admission, session and request lifecycle, control parsing, policy, pending actions, approvals, command permissions, replay prevention, cancellation, outbox creation, and side-effect dispatch.
- The inbound lifecycle has three distinct gates. **Ingress admission** verifies the HMAC-SHA256 signature against the exact raw webhook body before parsing, validates the configured session's `message.received` envelope and non-empty message identifier, authorizes only a direct non-group text message whose canonical sender and chat JIDs equal the configured authorized operator, atomically claims the unique OpenWA session and WhatsApp message identifier, and then acknowledges the webhook. Display names, phone-like message text, quoted metadata, dependency readiness, and model interpretation never participate in ingress admission. A duplicate is acknowledged but creates no second request, approval, reply, or dispatch.
- **Request acceptance and interpretation** occurs only after ingress admission. When Jarvis is idle, the broker creates the active request and the orchestration agent determines the required capability and, for terminal work, selects and explains the execution host. This stage does not wait for connector or worker readiness, does not keep the webhook open, and does not create a hidden queue.
- **Dispatch readiness** is checked immediately before each selected connector read, connector action, or worker execution. An unavailable selected dependency terminates the active request with an unavailable outcome; when audit is writable, Jarvis reports the selected dependency and reason without failover. Dependency unavailability never changes the prior webhook acknowledgement, triggers OpenWA retry, substitutes another execution host, or queues the request.
- The webhook request ends after durable ingress admission. Model calls, approval waits, connector work, and terminal execution never run inside it.
- Ingress uses the following complete disposition matrix. Every `2xx` response means the event received a terminal ingress disposition—admitted, duplicate, rejected, or safely discarded—not that assistant work succeeded.

| Inbound case | Durable state and assistant behavior | HTTP result |
| --- | --- | --- |
| Missing or invalid HMAC signature | Do not parse into an operator control, conversation history, active request, or pending action. Record only bounded transport metadata when safe. | `401` |
| Valid signature but invalid JSON, missing required envelope, blank session identifier, or blank message identifier | No assistant work or conversation history. Record a bounded malformed-event failure when durable state and audit are available. | `400` |
| Durable inbox state cannot be written | Do not claim or process the event. | `503` |
| Duplicate internal session and WhatsApp message identifier | Preserve the original disposition; create no new history message, request, approval, reply, or dispatch. | `204` |
| Authenticated event other than `message.received`, wrong configured OpenWA session, `fromMe` not exactly `false`, group message, status traffic, media, reaction, call, unsupported kind, non-text type, blank or whitespace-only body, mismatched direct-message sender and chat JIDs, unresolved sender identity, or unauthorized sender | Durably record only the bounded redacted disposition when audit is available, otherwise safely discard it. Do not retain the body in conversation history and create no request, reply, or side effect. | `204` |
| Valid authorized direct nonblank text while audit is unavailable | Durably claim the ingress key and retain the authorized inbound text in conversation history with a blocked-audit disposition. Create no active request and send no WhatsApp response. A fresh operator instruction is required after recovery. | `202` |
| Valid authorized direct nonblank text while audit and state are writable | Atomically claim the ingress key, append the authorized inbound text to conversation history, record admission and authorization audit evidence, and make it eligible for deterministic control handling or request acceptance. | `202` |

- Authenticated rejection and unsupported traffic always receive `2xx` after their disposition, so OpenWA does not retry routine V1 exclusions. Only authentication failure, malformed input that cannot be safely dispositioned, or failure to persist a claim uses non-`2xx`.
- Each connector owns one credential boundary and exposes a closed typed operation set. It independently validates operation, target, size, count, timeout, and V1 allowlist constraints. No connector exposes arbitrary HTTP, arbitrary OAuth scope, a raw credential, generic shell, arbitrary recipient selection, or excluded operations.
- The outbound messaging connector fixes the OpenWA session and destination to the admitted operator conversation. The model cannot select a different recipient.
- The audit service uses a separate identity and append-only store. The broker can append and query the bounded redacted view but cannot alter or delete prior records.

### Working session and control grammar

- A working session begins with an authorized request and ends through `/new` or configured inactivity. The default inactivity boundary is 60 minutes; allowed values are 15, 30, 60, 120, and 240 minutes. Genuine active processing suspends inactivity, while a pending action's independent ten-minute expiry continues.
- Complete normalized slash commands take precedence over approval phrases and ordinary requests. Matching is case-insensitive, trims surrounding whitespace, collapses repeated whitespace, and never uses fuzzy matching.
- Commands accept only the exact forms in the table. Extra tokens or missing required tokens produce usage guidance and no state change.

| Command | Deterministic effect |
| --- | --- |
| `/new` | Atomically cancel active work, invalidate the pending action, revoke session command permissions, end the conversation and working session, and start a clean session using persistent defaults. Conversation history, durable assistant memory, audit records, and persistent command permissions remain. |
| `/status` | Show the safe working-session identifier and inactivity boundary, model and reasoning, active-request phase and execution host, pending-action safe summary and expiry, command-permission count, and Ubuntu, Windows, OpenWA, and connected-service readiness. Never show credentials, connected-service cache, raw tool payloads, request working data, or terminal output. |
| `/cancel` | Cancel the active request and invalidate its pending action immediately. It does not end the working session or revoke command permissions. When idle, report that nothing changed. |
| `/model` | Show the current working-session model and canonical choices. |
| `/model <model>` | Set the idle working session to exactly one canonical model. The persistent default is unchanged. Refuse while a request or pending action is active. |
| `/reasoning` | Show the current working-session reasoning and canonical choices. |
| `/reasoning <level>` | Set the idle working session to exactly one canonical reasoning level. The persistent default is unchanged. Refuse while a request or pending action is active. |
| `/config` | Show persistent model and reasoning defaults and the inactivity boundary. |
| `/config model <model>` | Set the persistent model default for future working sessions. The current working-session model is unchanged. |
| `/config reasoning <level>` | Set the persistent reasoning default for future working sessions. The current working-session reasoning is unchanged. |
| `/config session-minutes <minutes>` | Set the current and future inactivity boundary to exactly 15, 30, 60, 120, or 240 minutes. |
| `/permissions` | List every active command permission's stable identifier, lifetime, execution host, exact normalized command, canonical working directory, creation time, and last-use time. |
| `/revoke <ID\|session\|persistent\|all>` | Revoke matching command permissions immediately, before acknowledgement. Revocation remains available during active work and prevents a matching approved-but-not-started terminal action from executing. |

- Mutating `/config` commands are refused while a request or pending action is active. `/status`, `/cancel`, `/new`, `/permissions`, and `/revoke` remain available during work.
- Request acceptance, host selection, milestones, proposals, and final outcomes carry stable bounded identifiers. Milestones are emitted only at material stage transitions.
- If an admitted ordinary message arrives while an active request exists and no pending action exists, Jarvis retains the inbound text in conversation history but creates no request, queues nothing, and does not append or otherwise modify the active request. When audit is writable, it records a bounded `request_refused_busy` event and sends exactly: `Request <request ID> is still active. Use /status or /cancel; V1 does not queue another request.` The same behavior applies while the request is interpreting, reading, preparing a proposal, dispatching terminal or connector work, cancelling, or awaiting terminal completion. If audit is unavailable, the message remains retained but no busy response is sent.

### Frozen actions and approval

- A pending action belongs to exactly one working session and active request, pauses that request, blocks unrelated work, and expires after ten minutes.
- The broker canonicalizes and stores the exact target, operation, arguments, material content, preview, digest, ownership, creation time, and expiry. Execution uses the stored payload, never a regenerated model payload.
- Every preview begins with the stable action identifier and expiry. It displays the exact service operation and material content. A terminal preview additionally displays execution host, normalized command, canonical working directory, material standard input, timeout, policy reason, and allowed choices. A vault preview displays the base commit, every canonical Markdown path, complete unified diff, and commit metadata.
- One proposal-envelope protocol applies whenever any exact preview exceeds one 4,096-character OpenWA message. Each bounded fragment contains the action identifier, complete proposal-content digest, one-based fragment number, total fragment count, and only its ordered slice of the frozen preview. Jarvis sends fragments in order and records the returned outbound identifier and gateway-acceptance result for each. The action remains in a non-confirmable `presenting` state until every fragment has known gateway acceptance; approval or rejection phrases received earlier change nothing and receive no new outbound response until presentation is complete. After all fragments are accepted, a final bounded message repeats the action identifier and digest, states that all fragments were presented, and displays the allowed choices. A failed or unknown fragment outcome invalidates the action, removes its executable pending payload, ends the active request, and requires a new request and newly presented proposal. Fragments are never selectively retried after an ambiguous outcome.
- Exact-action approvals that cannot create a command permission—including Gmail, knowledge-vault, history, and durable-assistant-memory changes—display `1 Allow this time | 4 Reject`. Mandatory-fresh terminal actions display the same choices. Permission-eligible terminal actions display `1 Allow this time | 2 Allow for this session | 3 Allow every time | 4 Reject`.
- This-time approval accepts exactly `yes`, `okay`, `ok`, `allow`, `approve`, `confirm`, `go ahead`, or `1` after whole-message normalization.
- Working-session permission accepts exactly `allow for this session`, `allow this session`, or `2`.
- Persistent permission accepts exactly `allow every time`, `always allow`, or `3`.
- Rejection accepts exactly `no`, `reject`, `deny`, `cancel`, `cancel action`, `don't do it`, `do not do it`, or `4`.
- Selecting `2` or `3` for an eligible terminal action atomically creates the displayed exact command permission and executes the pending action without a second confirmation. For an ineligible action, those replies change nothing and Jarvis repeats the available choices.
- Qualified text, multiple choices, reactions, fuzzy variants, and unrelated messages never approve, reject, execute, or alter the frozen proposal. `/cancel` has the same no-execution outcome as rejection but additionally cancels the owning active request.
- Rejection ends the paused request after removing the pending payload. Ten-minute expiry also ends the paused request, reports that nothing executed, and requires a new operator request and fresh proposal. Restart invalidates the proposal, interrupts the request, and prevents replay of every prior confirmation.
- Approval consumption, action-state change, optional permission creation, audit admission, and one dispatch/outbox record are atomic. Before dispatch, the broker rechecks ownership, expiry, digest, lifecycle, replay status, permission revocation, connector or worker identity, selected host, and audit availability.
- Completion, rejection, cancellation, expiry, or restart immediately removes the exact pending payload. Only redacted lifecycle evidence remains. Restart never permits an old confirmation to execute.

### Terminal policy and workers

- V1 terminal authorization is entirely deterministic. Gemini and every other model-based command classifier are deferred to V2.
- Policy precedence is fixed: hard prohibition; mandatory-fresh approval; protected-resource approval unless an exact command permission matches; exact command permission; provably safe read; approval for every other eligible action. An exact matching command permission satisfies the protected-resource approval requirement, but it never overrides a hard prohibition, mandatory-fresh classification, execution-host mismatch, canonical path or working-directory mismatch, argument or compound-structure mismatch, or revocation.
- A terminal action identity contains execution host, resolved executable or script path, complete arguments, canonical working directory, and normalized compound-command structure including operators, pipelines, order, and redirections. Inherited environment variables are not stored or compared, and the command inherits the worker environment. Executable or script contents and file metadata are not stored or compared; an exact command permission continues to match if content at an allowed path changes. This is deliberate path-based standing authority, not immutable-behavior authorization: a persistent permission authorizes whatever behavior the permitted executable or script path and inherited environment produce later. The authorized operator explicitly accepts that residual escalation risk. Canonicalization follows symlinks, junctions, and reparse points where possible.
- Every component of a compound command is parsed and authorized before execution starts. A prohibited component rejects the entire action; a mandatory-fresh component makes the entire proposal one-time-only. A reusable permission binds the complete normalized chain. If runtime failure occurs after an earlier component caused a side effect, the result and operator-facing failure identify which components started and which completed rather than presenting the compound command as wholly successful or wholly unattempted.
- Hard prohibitions cover broad or unresolved destructive targets, control or audit bypass, credential extraction or prohibited transmission, covert persistence, public control exposure, destructive Git history rewriting, evidence concealment, and activation of a trust-critical Jarvis component. No approval or command permission overrides them.
- Mandatory-fresh classes are system-level software installation, removal, or upgrade; materially dynamic shell evaluation that cannot be frozen; and downloading then immediately executing code.
- Protected resources include credential and key stores, authentication data, cloud CLI credentials, OpenWA pairing state, Jarvis credential boundaries, secret-bearing environment data, audit storage, deleted conversations, administrative backups, security-policy internals, other-user private files, and configured protected paths.
- A provably safe read must have known read-only semantics, no elevation or alternate identity, no protected-resource access, no network communication, no project or downloaded code execution, no dynamic evaluation or redirection, bounded scope, runtime, and output, and canonical target paths. Uncertainty requires approval.
- A command permission stores only the exact normalized rule, lifetime, creation and authorization provenance, last-use metadata, and revocation state. Session permissions end on session end or restart; persistent permissions remain until explicit revocation.
- Terminal actions are non-interactive. Material non-secret input is frozen, credential input uses the credential path, time and output are bounded, unexpected prompts fail, and cancellation terminates the process tree.
- Each worker authenticates as exactly one registered execution host. The Windows worker initiates an outbound private-overlay mTLS session and uses a Job Object for process-tree control. The Ubuntu worker uses a local authenticated channel and controlled process scope. Worker capabilities never expand policy.
- A worker accepts one new action for its own identity at a time and returns readiness, bounded milestones, tagged bounded output, cancellation status, and one terminal result. Disconnection or identity mismatch means unavailable, never failover.

### Google connector and OAuth

- Google uses one server-side External Web application authorization-code flow for one configured identity. The public OAuth callback is the only public Jarvis endpoint.
- The callback requires short-lived, cryptographically random, single-use state bound to the initiating operation, accepts only documented callback fields, hands the code to the Google connector, and returns a content-free result. It exposes no Jarvis control, message, state, approval, audit, worker, or general connector capability.
- The connector exposes only the following exact baseline:

| Service surface | Exact methods | OAuth scope | V1 handling |
| --- | --- | --- | --- |
| Gmail read | `users.messages.list`, `users.messages.get`, `users.threads.list`, `users.threads.get` | `https://www.googleapis.com/auth/gmail.readonly` | Approval-free bounded reads. No attachment download, label mutation, draft, settings, filter, forwarding, or delegation surface. |
| Gmail new send | `users.messages.send` | Incremental `https://www.googleapis.com/auth/gmail.send` | Approval-gated. Freeze every `To`, `Cc`, and `Bcc` recipient, subject, body, MIME content type, and other material send field. |
| Gmail reply | `users.messages.send` through a distinct typed reply operation | Incremental `https://www.googleapis.com/auth/gmail.send` | Approval-gated. Freeze the source message identifier, intended thread identifier, exact `To`, `Cc`, and `Bcc` recipients, subject, body, MIME content type, `In-Reply-To`, `References`, thread identifier supplied to Gmail, and every other material send field. The connector never infers or broadens recipients after approval. |
| Drive read/export | `files.list`, `files.get`, `files.export` | `https://www.googleapis.com/auth/drive.readonly` | Approval-free bounded metadata, content reads, and Workspace-document export within the text-only interaction boundary. |

- Do not request broader Gmail scopes such as full-mail, modify, or compose access, any Google Calendar scope, or any Drive write scope. The connector exposes no Gmail draft, modify, trash, delete, batch-delete, settings, forwarding, filter, or delegation operations; no Calendar operation of any kind; and no Drive create, upload, copy, move, rename, update, delete, permission, comment, revision, label, or sharing mutation.
- Gmail reply is not an alias for a new send. Its preview identifies the source and intended thread and shows all exact recipients and threading headers. Execution constructs precisely the approved MIME message and supplies the approved thread identifier. The connector verifies the returned message belongs to the intended thread and reports a mismatch or inability to verify as failure or unknown without retrying or silently issuing a replacement send.
- Gmail write scope is acquired incrementally. OAuth possession, consent, or newly acquired scope never constitutes approval and never executes a pending Gmail action that led to reconnection or consent.
- The connector rejects a token for a different Google subject rather than replacing the configured identity. It owns atomic refresh-token replacement within its private credential directory.
- Explicit disconnect, revoke, or integration removal revokes the Google grant and deletes local access- and refresh-token material. An `invalid_grant` or equivalent refresh failure stops Google calls, marks the connection disconnected, discards the invalid local credential, and asks the authorized operator to reconnect without indefinite retries. Reconnection never executes a previously pending or queued write.
- Production V1 must not depend on the seven-day refresh-token lifetime of an External application left in Testing status. It keeps only one live credential record for the configured Google identity and avoids repeated authorization and token churn.
- Gmail writes dispatch only the exact broker-approved frozen action. Calendar actions, destructive Google actions, and every Drive mutation remain absent even if a legacy credential technically retains broader scopes.

### Knowledge-vault connector

- The knowledge vault uses one service-account-owned dedicated clone on Ubuntu at a configured canonical path outside the Jarvis application repository. The private Git remote is the synchronization boundary; Jarvis does not edit the personal Windows Obsidian clone.
- A repository-scoped SSH identity is available only to the bounded vault Git process. Strict remote host-key verification is mandatory. Commit identity and the concise `jarvis:` subject convention are fixed deployment configuration; commit metadata excludes conversation content, secrets, messaging identifiers, and private request content.
- The connector fetches and fast-forwards before every vault request. If the remote is unavailable, reads may use the last synchronized clean clone only with an explicit staleness warning and synchronization timestamp. Writes require successful current synchronization.
- Reads may access ordinary files inside the canonical knowledge-vault root. Search is local and deterministic across paths, filenames, Markdown, tags, and YAML frontmatter. Exact-note reads accept an explicit canonical path or an unambiguous title. Ordinary Obsidian wikilinks and Markdown links resolve only within the canonical vault root. Results are bounded excerpts with note path and line references, and only request-relevant excerpts enter model context. There is no external content index, semantic embedding index, or durable vault-content cache.
- Writes may create or modify only Markdown files in configured note directories. Canonicalization rejects symlinks, junctions, submodules, hidden or excluded directories, non-Markdown files, and paths resolving outside the vault root.
- A write preview includes whether every note is new or modified and states that approval commits and pushes precisely the displayed patch. When the complete unified diff exceeds one outbound message, Jarvis splits it across ordered, numbered WhatsApp messages while keeping the entire sequence bound to one frozen proposal and one approval choice.
- After approval, the connector fetches again, requires the approved remote base, applies the exact patch to a clean tree, proves the resulting diff equals the approved diff, commits with the approved metadata, and pushes normally.
- A changed base invalidates the unexecuted proposal. A post-commit non-fast-forward preserves the local commit, reports the conflict, and blocks later writes pending manual recovery. Only the same unchanged commit may receive a small bounded retry after an unambiguous transient network failure.

### State, memory, history, audit, and credentials

- The Jarvis state store is a local SQLite database using transactional writes and WAL mode. It is authoritative for operational state, accessible conversation history, durable assistant memory, command permissions, and local full-text indexes.
- Working-session records retain stable identity, lifecycle timestamps, model and reasoning settings, conversation reference, live request and pending-action references, and session-permission identifiers. Terminal operational records remain for 30 days.
- Active-request records retain stable and originating-message identifiers, lifecycle and phase, timestamps, cancellation or interruption reason, configuration snapshot, action and tool correlation identifiers, and outbound-attempt state. Raw working content is excluded.
- Conversation history retains every admitted authorized-operator inbound text and every Jarvis outbound text verbatim and immutably. One working session defines one conversation. Corrections append rather than edit prior messages.
- Accessible history uses local full-text search and deterministic filters. Automatic retrieval is bounded; using an earlier conversation must be disclosed with a compact conversation and message-time pointer. V1 has no semantic history retrieval or external embedding index.
- Deletion requires an exact preview and confirmation, then moves immutable content into a separately permissioned deleted-conversation area outside Jarvis-readable paths. All Jarvis-readable indexes, excerpts, pointers, caches, and summaries are removed immediately; content-free tombstones remain for references.
- Durable assistant memory is created only by explicit instruction. Active memories are listable and persist until exact confirmed replacement or forgetting. Forgotten content becomes unusable while content-free audit metadata remains.
- Authorized messages remain verbatim even if they contain an API key, password, or other credential-class secret. An explicit remember instruction may likewise store credential-like content in plaintext durable assistant memory under the ordinary-state rule. Detected secret-bearing messages and memories remain deterministically searchable and inspectable but are excluded from automatic retrieval, retrieval indexes, and model context unless the authorized operator explicitly selects the exact record.
- Connected-service cache and request working data are request-scoped and discarded from their working stores on completion or restart. Raw prompts, retrieved content, tool results, terminal output, and model context do not enter operational state or audit content, but their complete payloads remain indefinitely in diagnostic traces and trace-bearing administrative backups. Text actually sent to the operator also becomes conversation history.
- Model-provider persistent conversation storage is disabled. Provider identifiers may be correlation metadata but never the sole copy of Jarvis history, memory, approval, or lifecycle state.
- Credential-class material deliberately supplied through the credential path lives outside ordinary state in service-specific plaintext credential-file boundaries. Static files are root-owned and exposed only to their consuming service. A connector that rotates credentials owns only its private directory and file. Credential-path material is excluded from source control, images, Compose rendering, ordinary state, environment variables, command lines, logs, model context, audit content, child-process inheritance, and routine backups and must never be copied into conversation history or durable assistant memory by the credential workflow. This isolation rule does not reject, delete, or rewrite credential-like text deliberately sent in an authorized message or explicitly stored in durable assistant memory; that content follows the preceding verbatim-retention and exact-selection rules.
- The audit record contains bounded redacted metadata for identity, correlation, operation and target category, policy and approval decisions, permission lifecycle, dispatch, execution, outbound attempts, restart, security failures, and outcomes. It references messages by identifier and excludes raw bodies, connected-service content, credentials, model reasoning, and unbounded tool or command output.
- Diagnostic traces retain the complete trace payload indefinitely: identifiers, timing, model and reasoning configuration, token use, span types, prompts, model inputs and outputs, message bodies included in model context, retrieved excerpts, tool and Codex arguments and results, connector results, terminal input and output captured by the request, errors, and outcome signals. No trace payload is automatically redacted, including detected passwords, tokens, API keys, private material, or other credential-class secrets. The trace store is therefore classified at the highest credential-bearing sensitivity of any retained payload, is isolated from Jarvis-readable paths, and is accessible for inspection or export only through manual administration outside Jarvis. Jarvis exposes no trace-browsing, trace-export, or trace-deletion command.
- Diagnostic traces never expire automatically and are never removed to relieve disk pressure. Removal, if ever required, is a separate manual administrative decision outside Jarvis. Trace append and storage failures are visible administrative degraded conditions; Jarvis must not begin a model, Codex, connector, or worker operation unless its full resulting trace can be retained within configured resource bounds.
- If required audit admission fails, the broker blocks every side effect, including all OpenWA replies, failure messages, `/status` responses, and degraded-state warnings. Inbound events may still be durably claimed and acknowledged according to ingress policy, but they create no assistant work while audit is unavailable and require a fresh operator instruction after recovery. Safe reads remain available only through the local administrative interface, which reports audit failure locally and does not dispatch an outbound WhatsApp message. There is no emergency journal and no unaudited fixed-destination exception.

### Messaging and network boundaries

- OpenWA remains the independently managed messaging gateway with Baileys as its sole active messaging engine. Its image pin, persistent volume, session, pairing state, database, stop grace, private-LAN administration, upgrade discipline, and recovery procedure remain authoritative and outside Jarvis ownership.
- Messaging readiness requires both a healthy OpenWA container and the configured messaging session in `ready` state. Jarvis never equates HTTP health with WhatsApp readiness.
- Inbound and outbound operations retain OpenWA's internal API session identifier. The human-readable session name is never substituted in message-history, reply, or send routes.
- A normal response to an admitted inbound message calls `POST /api/sessions/<internal-session-id>/messages/reply` with the admitted conversation JID, the current inbound message identifier as `quotedMessageId`, and text no longer than 4,096 characters. `POST /api/sessions/<internal-session-id>/messages/send-text` is used only when a threaded reply is intentionally not wanted.
- A successful OpenWA send means the messaging gateway accepted the message, not that WhatsApp delivered it. Jarvis stores the returned outbound message identifier and may update delivery state only from the relevant sent, acknowledgement, or failed status events. The audit and operator-facing result preserve the distinction between attempted, gateway-accepted, delivered when actually known, failed, and unknown.
- OpenWA reply and send operations have no client-supplied idempotency token. An ambiguous timeout, connection loss, or lost acknowledgement is recorded as unknown and is never retried automatically. Bounded history or outbound-status inspection may reconcile the outcome when possible; a new send requires a fresh explicit instruction.
- OpenWA and the inbound receiver share one private, non-published, two-member handoff network. No other Jarvis component joins it. This network addition requires one controlled OpenWA recreation and the complete established OpenWA verification ladder, but does not merge deployments or lifecycle.
- Container-to-container Jarvis communication uses authenticated service protocols over trust-segmented, private, non-published Docker networks. Cross-container mounted Unix-domain sockets are not required. The native Ubuntu worker uses a permission-restricted authenticated local socket; the Windows worker retains its outbound private-overlay mTLS session. The worker gateway binds only to the private-overlay interface. Administrative status and audit access are local or private-overlay-only.
- The registered HTTPS Google OAuth callback is the only public Jarvis endpoint. There is no public control API, webhook, dashboard, broker, audit view, connector, worker-control port, or shell.

### Deployment, operations, and recovery

- Jarvis is an independent Docker Compose project on the Ubuntu control host. Containers use distinct non-root identities, read-only root filesystems except explicit state or temporary mounts, dropped capabilities, `no-new-privileges`, bounded PIDs, and only their own configuration and credential mounts.
- The control plane separates the inbound receiver, capability broker and state owner, orchestration agent, audit service, Google connector, vault connector, outbound messaging connector, worker gateway, and public OAuth callback according to their trust boundaries. The Ubuntu and Windows execution workers remain native least-privileged services.
- No Jarvis container receives privileged mode, the Docker socket, broad host mounts, or the host process namespace.
- Non-secret configuration is one root-owned, read-only validated document. Unknown keys, missing values, floating image references, invalid permissions, inconsistent identities, or cross-field errors prevent readiness.
- The activated pinned release starts automatically and may be relaunched after failure or reboot. Automatic recovery never pulls images, changes digests, migrates state, reloads trust-critical configuration, or activates a different release.
- Before accepting new work after restart, the broker reconciles every durable inbox, active-request, pending-action, dispatch, outbox, and outbound-attempt record. Every nonterminal request—including an admitted inbound message for which processing had not begun—is marked interrupted and is not started or resumed automatically. Known-unattempted connector, worker, or outbound dispatches are closed without execution. Attempts lacking a confirmed result become unknown and are never retried automatically. Pending payloads are removed, session command permissions are revoked, and inconsistent records fail closed with redacted audit evidence and an administrative degraded state. The authorized operator must send a fresh instruction for every unfinished request.
- Ingress admission requires only valid identity and event structure plus writable durable inbox state; it does not depend on model, connector, worker, or OpenWA outbound readiness. Request acceptance requires an idle working-session slot and writable authoritative state and audit. Dispatch readiness separately checks the exact selected connector or worker immediately before use. Unrelated safe capabilities may remain available when one connector or worker is degraded, but an unavailable selected dependency terminates the active request without queueing or failover.
- Graceful shutdown stops admission, durably acknowledges claimed inbound messages, cancels or interrupts work within a bound, invalidates pending actions, flushes state and audit writes, and stops Jarvis without stopping OpenWA.
- Local observability consists of narrow health checks, sanitized rotated structured logs, the safe `/status` view, and an administrative status command reporting component readiness, messaging readiness, audit writability, backup freshness, host availability, release identity, and resource pressure without sensitive content.
- Administrative backups run nightly and before upgrades, active-configuration changes, or migrations. They include consistent state, audit, deleted-conversation data, the entire full-payload diagnostic-trace store, non-secret configuration, deployment metadata, image digests, and schema version. Because traces retain literally all payloads, backups may contain credential-class secrets even though service credential files and private keys remain excluded. Backup storage, access, transport, restore, and inspection use the same highest-sensitivity manual-administration boundary as the trace store. OpenWA data and pairing state, ephemeral working data not already captured in traces, and caches remain excluded.
- Backup snapshots are local, outside Jarvis-readable paths, retained indefinitely, and restored only through manual administration. Restore validation covers checksums, ownership, permissions, SQLite integrity, audit readability, schema and release compatibility, and separate credential reprovisioning.
- The Jarvis deployment has an aggregate ceiling of 1.25 GiB RAM and two CPU cores with per-component limits. It adds no local model, embedding model, Redis, PostgreSQL, queue service, object store, metrics stack, or other resident infrastructure tier.
- Terminal stdout and stderr are capped independently at 1 MiB. Connector result count and size, model context, agent turns, execution time, temporary disk, and process scope are bounded.
- Disk warnings begin below the configured warning threshold. Below 2 GiB free, when full trace retention for a proposed operation cannot be guaranteed, or when audit append is unavailable, Jarvis enters degraded mode. Trace data is never automatically deleted. Audit failure blocks every WhatsApp response and leaves safe reads only on the local administrative interface; low-disk or trace-capacity failure blocks new model, Codex, connector, worker, and other trace-producing work until manual administration adds capacity or otherwise resolves the condition.
- All tunable bounds use the conservative defaults below. Configuration may lower a value but cannot exceed its hard maximum; startup rejects missing, zero, negative, or over-maximum values. A fixed value is not configurable in V1.

### Implementation slicing

- Implement contract types and deterministic foundations first: configuration validation, identifiers, clocks, typed operations, error envelopes, SQLite transactions, redaction, audit admission, control grammar, lifecycle, replay claims, and outbox state.
- Add the capability broker and controlled test implementations before any live connector. All side-effect paths must pass through the broker's audit gate and atomic approval-to-dispatch transaction.
- Add the inbound receiver and outbound messaging connector against the pinned OpenWA contract while keeping the production handoff network change out of implementation activation.
- Add the Agents SDK orchestration adapter and bounded Codex specialist interface after deterministic authority is testable without a model.
- Add Google, knowledge-vault, worker-gateway, Ubuntu-worker, and Windows-worker contracts one at a time, retaining closed schemas and the primary control-plane test seam.
- Add deployment manifests, health checks, administrative status, backup/restore, maintenance, upgrade, rollback, and resource controls only after application behavior passes automated acceptance.
- Treat activation, credentials, network changes, service definitions, worker registration, firewall changes, and production OpenWA attachment as a separate manual-administration phase after implementation and review.

## Testing Decisions

- The primary automated seam is: feed a signed OpenWA `message.received` event into the Jarvis control plane and observe the externally visible result—outbound reply, frozen proposal, connector or worker dispatch, state transition, and redacted audit evidence.
- Automated tests run the real inbound receiver, capability broker, deterministic control grammar, policy engine, SQLite state, replay protection, pending-action lifecycle, permission handling, audit gate, and outbox behavior.
- Controlled connector and worker contract implementations replace remote or nondeterministic edges. They expose the same closed typed contracts as production Google, knowledge-vault, OpenWA outbound, orchestration-agent, Codex, and execution-worker adapters and allow deterministic readiness, response, delay, disconnection, failure, and ambiguous-outcome injection.
- Tests control clock, identifiers, session readiness, connector readiness, worker identity and availability, audit append results, disk state, external outcomes, and restart boundaries. This makes expiry, inactivity, replay, cancellation, recovery, retry, and no-failover behavior deterministic.
- Good tests assert externally meaningful behavior and security invariants rather than internal call order or private implementation structure. Assertions cover outbound text, safe proposal content, exact dispatch payloads, absence of dispatch, state visible through supported views, persisted lifecycle results, and redacted audit evidence.
- The validated pure control parser and reducer prototype is prior art for message normalization, command precedence, approval phrases, permission choices, and lifecycle transitions. Production tests exercise those behaviors through the higher control-plane seam; narrow unit tests may supplement the seam for exhaustive parser and canonicalization tables.
- Contract tests verify that each production connector accepts the same typed operations and returns the same bounded outcomes as its controlled implementation. They also verify rejection of unknown fields, excluded operations, arbitrary targets, wrong identities, oversized results, and unsanitized errors.
- Ingress-disposition tests cover missing and invalid signatures, signed malformed JSON, missing envelope fields, wrong event and session, duplicates, unauthorized and unresolved senders, groups, `fromMe` echoes, status traffic, media, reactions, calls, unsupported kinds, non-text content, blank text, whitespace-only text, oversized text, audit outage, and unwritable inbox state. Every case asserts the exact HTTP status, durable disposition, conversation-history effect, audit effect, and absence or creation of assistant work.
- Busy-message tests admit a second ordinary authorized message during interpretation, connector reads, proposal preparation, terminal or connector dispatch, cancellation-in-progress, and terminal completion. They assert durable conversation-history retention, no active-request mutation, no queue or second request, one bounded `request_refused_busy` audit event and exact busy response when audit is writable, and no outbound response when audit is unavailable. Pending-action cases remain governed by the separate approval grammar.
- Property and table-driven tests cover message normalization, replay keys, approval consumption, expiry boundaries, exact-action digests, command canonicalization, compound-command policy precedence, command-permission matching, path containment, redaction, bounded output, and state-machine invariants.
- Proposal-envelope tests cover every approval-gated action type at one-message and multi-message boundaries; ordered numbering and total counts; identical action identifiers and content digests on every fragment; early, qualified, and replayed approvals; final-prompt gating; failed and unknown fragment outcomes; invalidation without selective retry; and the rule that execution uses the same fully presented frozen payload.
- Restart tests prove that active requests become interrupted, pending payloads are removed, session permissions are revoked, persistent permissions survive, request working data is cleared, and no model call, connector operation, terminal process, or ambiguous side effect resumes.
- Restart-reconciliation tests cover durably admitted-but-unstarted messages, processing requests, known-unattempted dispatch and outbox records, attempted-without-acknowledgement operations, outbound attempts with and without returned message identifiers, and inconsistent inbox/action/outbox combinations. Every unfinished request requires a fresh operator instruction; no stale reply or side effect is sent after recovery.
- Failure tests prove the four-part operator-facing failure format, stable bounded error code and request identifier, secret and personal-identifier exclusion, correct definite-versus-unknown outcome statement, bounded retry rules, and no automatic retry of ambiguous side effects.
- Security tests cover bad signatures, wrong sessions, missing identifiers, malformed bodies, groups, status events, media, reactions, unresolved identities, unauthorized senders, duplicate webhooks, replayed approvals, prompt injection in every untrusted-content source, malformed model proposals, direct connector attempts, audit failure, worker identity mismatch, host substitution, trust-critical activation attempts, Codex `danger-full-access`, Codex internal-approval bypass, disallowed Codex push/history rewriting, workspace-write without an exact approved proposal, and unverified Codex mutation claims. Audit-failure cases assert that no WhatsApp reply, failure, `/status`, or degraded warning is dispatched and that only the local administrative interface can expose safe-read results and recovery state.
- State tests cover working-session inactivity, `/new`, `/status`, `/cancel`, model and reasoning configuration, one-active-request and one-pending-action limits, ten-minute expiry, history retrieval disclosure, exact deletion preview, durable assistant memory lifecycle, credential-like content exclusion, operational retention, indefinite full-payload trace retention, literal credential retention inside trace payloads, manual-admin-only trace access, trace inclusion in backups, no automatic trace deletion, trace-capacity degraded behavior, and redacted audit filtering/export.
- Terminal-permission tests explicitly prove the accepted path-authority contract: a structurally identical permission continues to match after executable or script contents, file metadata, or inherited environment values change, while host, path, arguments, working directory, compound structure, higher policy rules, and revocation still control matching.
- Lifecycle tests distinguish ingress admission, request acceptance and interpretation, and dispatch readiness. They prove that connector or worker availability never changes webhook acknowledgement, unavailable selected dependencies terminate without queue or failover, and readiness is rechecked only at the relevant dispatch boundary.
- Integration tests cover real local process boundaries, private container networks, the Ubuntu worker's authenticated local socket, SQLite WAL behavior, append-only audit permissions, OAuth callback state consumption, exact Gmail and Drive method/scope allowlists, typed Gmail reply source/thread/recipient/header binding and returned-thread verification, the absence of Calendar operations from v1, worker mTLS identity, process-tree cancellation, vault Git race handling, the universal proposal-envelope protocol, OpenWA internal-session-ID routing, reply correlation, 4,096-character bounds, returned outbound identifiers, gateway-acceptance versus delivery state, and ambiguous-send behavior without using production credentials.
- Limits tests exercise every conservative default and hard maximum, reject over-maximum configuration at startup, prove deterministic truncation or refusal behavior, reserve full-trace capacity before work, and run the specified automated and supervised endurance workloads with five-second measurements and the ten-minute settling window.
- The separately required supervised acceptance suite runs against real OpenWA, the configured Google account, the private knowledge vault, Ubuntu, and Windows. Test data is conspicuously labeled, real side effects are reversible and approved through the production control flow, and excluded or destructive behavior is verified only through rejection.
- Supervised acceptance covers build and configuration, network exposure, OpenWA preservation, admission and replay, receiver outage plus shutdown/retry races, the three admission/readiness gates, control grammar, universal oversized-proposal presentation, prompt-injection containment, exact Gmail and Drive scopes and reads, approved Gmail new-send and typed reply behavior, Calendar refusal, Google revocation/reconnection without stale Gmail execution, knowledge-vault reads and approved writes, terminal policy and partial compound-command outcomes, accepted mutable path-authority behavior, both workers, full diagnostic traces and backup recovery, audit-down local-only behavior, failure messages, resource endurance without automatic trace deletion, upgrade and rollback, and full-host reboot recovery.
- OpenWA acceptance requires the established complete verification ladder after the single controlled handoff-network attachment: deployment validation, container health, messaging session readiness, exact inbound text, confirmed outbound receipt, retained pairing after controlled recreation, stop-grace verification, unchanged LAN and firewall exposure, and settled resource checks. A WhatsApp `LOGOUT` stops testing without repeated recreation or re-pairing.
- Acceptance fails on any authorization or approval bypass, secret or personal-identifier disclosure, duplicate side effect, unexplained external outcome, unauthorized network exposure, missing required audit evidence, resource breach, unrecoverable backup, automatic trust-critical activation, or regression of the verified messaging gateway. A failed row remains an implementation blocker until retested or the V1 contract is deliberately reopened.

- Modifying, upgrading, re-pairing, restarting, or otherwise changing the existing OpenWA deployment.
- Scheduled tasks, proactive monitoring, reminders, background automation, assistant-initiated conversations, or unsolicited health alerts.
- Voice notes, images, documents, reactions, and every other non-text WhatsApp interaction.
- Multiple authorized operators, group-chat control, multiple active requests, parallel pending actions, or request queueing.
- Automatic failover between Ubuntu and Windows or silent host substitution.
- Model-based terminal authorization, including Gemini classification; the retained Gemini research is V2 background only.
- Destructive Google actions, Drive mutations, arbitrary OAuth scopes, or generic Google API access.
- Knowledge-vault deletion, rename, non-Markdown mutation, external content indexing, semantic embeddings, autonomous merge resolution, rebase, cherry-pick, force-push, or history rewriting.
- Broad destructive terminal actions, credential extraction, public control exposure, control or audit bypass, covert persistence, evidence concealment, and activation of trust-critical Jarvis components.
- A public Jarvis control API, public inbound webhook, public dashboard, public broker or connector endpoint, public worker control, or internet-accessible shell.
- Local model inference, local embedding models, Redis, PostgreSQL, general message queues, object storage, Kubernetes, or an external observability stack.
- Cloud synchronization of Jarvis state, external semantic retrieval of conversation history, or model-provider authority over history and lifecycle.
- Permanent erasure or Jarvis-driven restoration of deleted conversations, deletion of permanent audit records, or automatic deletion of administrative backup snapshots.
- Exactly-once guarantees across external APIs after an ambiguous outcome. V1 prevents local replay and reports unknown outcomes without automatic retry.
- Protecting plaintext credential files from root compromise or offline disk access; that is an accepted V1 trade-off.
- Replacing the manual administrator for credentials, trust-critical activation, production network changes, recovery, upgrades, rollback, conflict resolution, or destructive exclusions.

## Further Notes

- The reconciled canonical glossary is authoritative. Implementations, tests, messages, documentation, and follow-on tickets must use terms such as messaging gateway, authorized operator, ingress admission, request acceptance, dispatch readiness, working session, active request, pending action, approval-gated action, command permission, orchestration agent, capability broker, connector, execution host, knowledge vault, request working data, audit record, and diagnostic trace with their defined meanings.
- The messaging gateway and assistant behavior remain separate contexts even though they share a private handoff network. OpenWA owns pairing and transport; Jarvis owns admission and assistant behavior.
- The exact registered OAuth URL, canonical operator and session identifiers, service identities, host registrations, note directories, private remote, credential material, and similar deployment values are configuration or credentials. They must not be embedded in source, test fixtures, this specification, logs, audit content, or operator-facing failures.
- The resolved Wayfinder tickets, linked research, validated interaction prototype, domain glossary, accepted messaging-engine ADR, and OpenWA deployment documentation remain the decision record behind this synthesis. Where their wording conflicted, contained a documented synthesis error, or left behavior open, this specification records the authorized operator's explicit resolutions: an exact command permission may satisfy protected-resource approval subject to every higher policy constraint; containers use private non-published networks while the native Ubuntu worker uses an authenticated local socket; every unfinished request requires a fresh operator instruction after restart; full diagnostic traces including credentials are retained and backed up indefinitely; reusable terminal permissions deliberately retain path-based authority across executable-content and inherited-environment changes; and audit failure permits no WhatsApp delivery.
- Implementation completion is not production activation. The implemented release becomes eligible for manual activation only after code review, automated verification, deployment review, credential provisioning, controlled OpenWA handoff-network attachment, and the complete supervised acceptance matrix.
